# Protected code admission, before real identity

`code-admission.py` installs only the exact public file rows of the independently
reviewed source19 catalog. It holds all hash-checked packet bytes before native
confirmation. Every destination must be absent. It does not generate/read keys,
sign, reload/load/start/stop a unit, select a Release, change Owner/Grant, or open
business journals. The complete candidate is placed in its unselected R17 path;
placing its files is not production Release installation or activation.

The initial installer is not already trusted just because it is in a packet.
A real HostAdmin must review its source, the initial launcher/root loader, the
external installer/catalog SHA-256 pins, complete target list and permissions.
`tools/code-admission-launch.py` uses fresh `sudo -k` authentication; an isolated
root Python loader holds and hashes the exact installer bytes before compiling
them. It never imports a module from the writable packet. The installer then
requires the same authenticated foreground HostAdmin/Jenn launcher and
terminal chain, plus the exact `INSTALL_CODE` hash.
Neither a chat approval nor `describe` substitutes for that native acceptance.
This is `TRUSTED_HOST_ADMIN_CODE_ONLY`: it does not attest the caller's physical
location, Human identity, key holding, or enrollment. A globally active GUI
session is not accepted as evidence of any of those facts. The separate G3
Ubuntu local `auth_self` gate remains mandatory for Human confirmation.
No such bootstrap was executed in the engineering stage.

The five-minute window starts after actual acceptance. Every directory creation
and file create is guarded immediately before the effect. Existing code is never
overwritten. Append-only per-file INTENT/RESULT records distinguish known writes
from ambiguous outcomes. A second invocation reads existing state; it cannot
continue a partial install or repeat an unknown write. Preserve partial files and
receipts for explicit scoped recovery. Source19 drift refuses without renewing
any old plan or automatically choosing another revision.

`readback` verifies every created inode, hash and mode. `remove-unused` needs a
new exact native confirmation and removes only recorded, unchanged files while
retaining all receipts. It refuses identity/proposal/approval/publication use,
a running approval socket, or any matching unit already loaded in systemd.
`list-units` is a read-only loaded-object query; this entry does not use `show`
to implicitly load installed units. Unknown install/removal outcomes refuse
further effects. It does not promise automatic recovery after an unknown write.

The identity helper has its own four-file source freeze and separate native
`HOST_ADMIN_CUSTODY` admission. That stage may generate/seal two real keys only
after its exact approval. Host administrator custody is stated explicitly and
is not a claim of Human-exclusive private-key possession or civil identity.

21/22 protocol and persistent receiver tests are engineering evidence only.
The protected production signer/backend entry and physical selector/recovery
integration are still unimplemented. V is **NOT_PROVEN**; this packet does not
approve G2/G3, issue configuration21, or enable Owner retirement. Standalone
identity G2/G3 remain separate from V; V blocks production21/22 delivery and
recovery/activation, rather than requiring those production effects first. The existing
formal production installer remains blocked. Keep that gate until the real
entry is implemented, independently reviewed, admitted and read back.
